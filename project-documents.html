1. 项目摘要

项目名称：MedScribe HK —— 香港临床口述智能病历助手

一句话描述：医生用粤语、英语或中英混合口语口述诊疗过程，系统完成"多语言转写 → 临床要素抽取 → 模板化结构化报告生成 → 医生校审确认"的闭环，输出符合医院报告规范的病历初稿。

核心价值主张：把 3–5 分钟口述变成 1 分钟内可审阅的病历初稿，且不改变医生现有的书写与审阅习惯。

2. 问题与目标用户

用户说明
主要：门诊 / 住院医生英文撰写病历、口语混用粤英，看诊后需快速完成病历整理，每日多次
次要：病案室 / 质控人员检查病历完整性与模板合规性，退回不规范记录
受影响：患者希望医生把注意力放在问诊而非打字上，并确保健康数据被安全处理

问题场景：门诊接诊后、查房后或交班前，医生需把刚发生的诊疗过程整理成结构化病历／报告。

编号问题描述状态
P-01键盘录入或模板填空占用问诊后时间，高峰期为每份病历数分钟待验证（ASSUMPTION-01）
P-02粤语 + 英语 + 中英混合病名/药名的表达，通用语音输入识别效果明显下降待验证（ASSUMPTION-02）
P-03模板随专科与报告类型而变，手工复制粘贴易漏项、错项（过敏史、剂量、随访）待验证（ASSUMPTION-03）

1. 概述与用户

1.1 问题回顾

香港临床医生需要在有限时间内完成病历与报告书写，而其口语表达普遍为粤语、英语与中英混合医学术语。现有工具缺少"多语言转写 + 临床要素结构化 + 模板化报告 + 人工校审"的完整闭环（详见 proposal.md §4.2）。

1.2 目标用户

用户需求在本 MVP 中的角色
门诊 / 住院医生（主要）用最短时间把口述变成可提交的病历初稿唯一操作者：录音、校审、签署、导出
病案室 / 质控人员（次要）病历字段完整、格式合规MVP 仅通过导出格式间接服务，无独立界面
患者（受影响方）数据不被滥用非操作者；由隐私与数据保留规则保护

1.3 预期价值

将一段 3–5 分钟的口述，转化为一份医生可在 1 分钟内完成审阅的结构化报告初稿，且初稿中每个临床要素都能追溯到原始音频片段。

1.4 与提案证据的关联

本 PRD 依赖的假设（ASSUMPTION-01 至 05）及其验证状态见 proposal.md §3.2。本版本中相关假设尚未验证，因此以下需求中的量化目标均为待实测确认的目标值，而非已达成结果。

2. MVP 范围

MVP 包含 5 个核心功能，共同构成一条完整用户任务；任何一项缺失都会导致该任务不成立。

编号核心功能为什么必须包含
F1会话录音 + 多语言 ASR 转写（粤 / 英 / 中混合，含医学术语增强）是整个链路的输入；没有可读的转写文本，后续全部不成立
F2临床要素抽取（Subjective / Objective / Assessment / Plan）把连续口语变成有结构的临床信息，是"能用的病历"与"一堆文字"的分界
F3模板化结构化报告生成（按报告类型选择模板）医生要交付的是符合规范的报告，而非自由文本；模板决定字段与顺序
F4医生校审界面（逐字段查看 / 编辑 / 采纳 / 拒绝 / 签署）临床安全的必要环节：AI 输出必须经医生确认才能成为病历
F5术语库管理 + 会话本地存档支撑 F1/F2 的领域词表；同时提供可复现的评估与回归测试数据

范围取舍原则：先跑通"一条端到端细线"（一个报告类型、一个科室模板、一种语料组合），再横向扩展模板与语种覆盖。

3. 明确排除项（Out of Scope）

排除项原因
真实患者数据接入合规与隐私风险超出课程项目可控范围；MVP 使用合成的模拟口述语料
EHR / eHRSS 实时对接（HL7 FHIR API 写入）需要医院侧授权与接口文档，周期不可控；MVP 以导出文本 + JSON 替代（见 FR-09）
移动端 App与 MVP 用户任务无关，Web 界面已足够验证核心价值
多说话人分离（多人查房场景）显著提高技术难度；MVP 限定单人连续口述
模型微调（fine-tuning）需要大规模标注数据与算力；MVP 先用提示工程 + 术语库，微调列入长期计划
多专科模板全覆盖模板适配能力通过 2–3 个模板验证即可证明可行性；穷举无额外学习价值
用户账号体系 / 单点登录MVP 为单机单用户或演示角色模式；系统不做权限分级（见技术设计 §8）
公网部署与多租户本地运行即可满足课程要求，且避免患者数据外流
自动诊断或治疗建议超出产品定位，存在临床与法律风险；系统只做"整理"，不做"判断"

4. 用户旅程与原型

4.1 端到端主流程

[S1 新建会话] → [S2 口述录音] → [S3 转写结果核对]
                                        ↓
[E 导出/粘贴] ← [S5 校审与签署] ← [S4 结构化初稿 + 模板选择]
                        ↑
              （缺失要素提示 / 低置信度标记）

4.2 关键界面与交互

界面主要元素关键决策点
S1 会话首页新建会话、历史会话列表（本地）、术语库入口是否需要继续上次未完成会话
S2 录音页录音按钮、时长计时、音量指示、可选实时字幕开关、暂停/继续是否允许超时自动停止（见 BR-01）
S3 转写核对页带时间戳的分段转写文本、每段语种标签、低置信度高亮、手动修正框是否接受转写直接进入抽取（低置信度段落建议先修正）
S4 结构化初稿页左侧 SOAP 四栏，右侧模板选择器（门诊记录 / 出院摘要 / 影像报告）模板选错时需可切换并保留已确认内容
S5 校审页字段卡片：AI 值 + 音频跳转按钮 + 采纳/编辑/拒绝；未确认项计数；签署按钮存在未确认字段时禁止签署（BR-10）
E 导出页预览成品、复制为纯文本、下载 PDF、下载 JSON导出后会话锁定（BR-11）

4.3 重要决策点说明

  1. 录音结束后的处理时机：MVP 采用"录音结束后一次性提交"（准实时），不做逐字流式转写。理由：降低复杂度，避免在音频不完整时反复触发抽取与生成。
  2. 模板切换时机：允许在 S4 重新选择模板并重新生成；已校审字段的修改以字段级差异保留，不要求医生重做。
  3. 要素缺失处理：若口述中未提及某必要字段（如过敏史），系统标记为"未提及"并要求医生确认，绝不自动填充推测内容（BR-03）。

5. 功能需求

每条需求均使用稳定 ID，便于在技术设计与测试用例中交叉引用。
ID需求可观察的预期行为
FR-01会话创建与录音用户可新建会话并录制音频；录音过程中显示已录时长；暂停与继续不丢失已录内容；结束后生成一个本地音频文件
FR-02多语言转写对 ≥ 10 秒的有效音频，系统输出带时间戳的分段文本；每段标注识别语种（粤 / 英 / 混合）；对置信度低于阈值（默认 0.6，可配置）的片段加高亮标记
FR-03术语纠正转写文本中命中术语库的词条按下述优先级替换：术语库精确匹配 > 术语库模糊匹配（编辑距离 ≤ 2）> 原始 ASR 输出；替换行为在界面上可见并可一键撤销
FR-04临床要素抽取系统把转写文本划分为 S / O / A / P 四类要素；每个要素必须携带指向原始转写片段的引用（片段 ID + 时间戳）；无法归类的内容进入"未分类"区，不丢弃
FR-05模板化报告生成用户选择模板后，系统按模板字段顺序生成报告初稿；模板中未被口述覆盖的字段显示为"未提及"占位，而非空白或猜测内容
FR-06缺失与风险提示若模板要求的必填字段在口述中缺失，界面显示缺失清单；若生成内容与音频原文存在明显不一致（如药名或剂量不匹配），标记为"待核实"
FR-07逐字段校审医生对每个字段可执行"采纳 / 编辑 / 拒绝"；系统保留 AI 原始值与编辑后值的差异记录；每个字段可一键跳转到对应音频时间点
FR-08签署所有必填字段均已确认（采纳或编辑）后，"签署"按钮可用；签署记录包含时间戳与操作者标识（演示角色）
FR-09导出支持三种导出：纯文本（可直接粘贴进 EHR）、PDF（含模板排版）、JSON（字段级结构，含来源引用）。导出后该字段内容标记为锁定
FR-10会话存档与重放历史会话可重新打开，查看转写、抽取结果、校审差异与导出记录；支持按会话删除（见 BR-12）

6. 业务规则与边界情况

6.1 业务规则

ID规则
BR-01单次录音上限 15 分钟；达到上限时自动停止并提示，不丢弃已录内容。长度超过阈值的会话在转写时按段落切分处理
BR-02有效音频定义为时长 ≥ 10 秒且非静音（信噪比不足时提示重新录制）
BR-03禁止编造：任何未在口述中出现的临床内容，一律以"未提及"呈现；系统不得推断诊断、剂量或过敏史
BR-04术语库优先级：精确匹配 > 模糊匹配（编辑距离 ≤ 2）> 原始输出；术语库更新后需可重新运行纠正（可复现）
BR-05药物名称与剂量必须以音频原文为依据；若 ASR 结果与术语库药名冲突，标为"待核实"而非自动替换
BR-06模板缺失时的回退：若所选模板未注册，系统给出提示并回退到"通用 SOAP 模板"，同时记录该事件
BR-07模板中的字段分为"必填"与"可选"；必填字段缺失即触发 FR-06 的缺失提示
BR-08中文与英文输出规则：报告正文默认保留英文医学表达（对齐香港病历习惯），可在导出时选择"中英对照"模式
BR-09低置信度片段默认不参与自动要素抽取的最终定稿，需医生在 S3 确认或修正后再进入 S4
BR-10存在未确认的必填字段时，禁止签署；导出同样被阻止
BR-11签署并导出后，报告内容锁定为只读；如需修改必须"另建修订版本"，原版本保留
BR-12数据保留：会话默认本地保存；提供"删除会话"功能，删除后音频、转写与报告一并移除，并在存档中记录删除事件

7.3 量化指标的测量方法（必须可复现）

指标 1：ASR 字错率（CER / WER）

  • 测试集：research-plan.md §4 定义的 ≥ 1 小时合成语料，其中留出 20 分钟作为固定回归集（冻结后不再改动）；
  • 计算：中文部分按字符编辑距离，英文部分按词编辑距离，分语种报告，混合句单独统计；
  • 报告要求：同时给出平均值与最差语种值；不得只报告最优结果。

指标 2：结构化初稿准确率

  • 评分单位：模板字段（field-level）；
  • 评分量表：每个字段 1.0 = 内容与参考标注一致；0.5 = 内容正确但位置/格式不符（如要素归错栏目）；0.0 = 错误、缺失或编造；
  • 准确率 = Σ字段得分 ÷ 字段总数；
  • 评分方式：双人独立评分 + 分歧仲裁，抽样 ≥ 20 份报告；评分量表需在评分前冻结并登记版本。

AI-01 多语言 ASR 转写

项目说明
目的把粤 / 英 / 中混合的临床口述转成带时间戳文本
允许的数据访问仅当前会话音频；不读取历史会话音频、不读取系统其他文件
期望输出分段文本 + 时间戳 + 语种标签 + 置信度

AI-02 临床要素抽取

项目说明
目的将转写文本划分为 S / O / A / P 并保留来源引用
允许的数据访问仅当前会话的转写文本与术语库；不发送音频，不发送其他会话内容
期望输出结构化要素列表，每项含类别、文本、来源片段 ID 与时间戳；无法归类内容进入"未分类"
失败行为抽取失败 → 保留转写文本、允许重试；不得用默认值填充；不得推断未提及内容（BR-03）
评估示例20 份标注样本上计算要素归属准确率与"丢失语句率"；AC-04 覆盖主流程
成本限制单次抽取的 token 上限与调用次数上限
需用户确认的操作抽取结果默认处于"待确认"状态，任何字段进入报告前需医生确认（FR-07）

AI-03 结构化报告生成

项目说明
目的按模板生成符合报告规范的初稿
允许的数据访问当前会话已确认的要素 + 模板定义；禁止访问其他会话
期望输出按模板字段组织的初稿，字段值必须来自要素内容，未覆盖字段为"未提及"
失败行为生成超时或校验失败（如字段缺失、出现无来源内容）→ 阻止输出并提示；不允许输出含无来源内容的报告
评估示例按 §7.3 指标 2 的字段级评分量表评测；额外统计"幻觉字段数"（有内容但音频中无依据的字段），目标为 0
成本限制每份报告的生成调用上限（含最多 1 次自动重试）
需用户确认的操作① 模板选择；② 每个字段的采纳/编辑；③ 签署（FR-08）；④ 导出（FR-09）。系统不得自动签署或自动导出

通用原则

  1. AI 生成内容一律以"初稿"呈现，界面必须持续显示"待医生校审"状态标识；
  2. 每个 AI 输出字段都必须可追溯到来源（音频时间点或要素 ID），无法追溯的内容不得进入报告；
  3. 提示词模板与模型版本号需记录在报告元数据中，便于复现与追责。

2. 技术选择

层选择理由更简单的替代方案
前端React + Vite + TypeScript校审界面交互状态多（字段级编辑、差异显示），组件化便于维护单页原生 HTML + 少量 JS，或 Streamlit；若进度紧张可退化为 Streamlit 原型
后端Python + FastAPI与 ASR/LLM 生态同为 Python；自动生成接口文档便于团队协作纯脚本 + 命令行，但无法支持界面对话
ASR本地 faster-whisper 为主，云 ASR API 为可选增强本地运行满足隐私约束（NFR-04），成本可控；云 API 用于精度对比仅用云 API：精度可能更高，但违反"数据不出本机"的默认假设
语言模型通用 LLM API（结构化 JSON 输出）+ 提示词约束团队精力应放在术语、模板与校审闭环，而非模型训练本地小模型：隐私最好，但中文医学结构化质量需实测，可能不达标
输出约束JSON Schema + 后端校验（pydantic）防止 LLM 返回自由文本导致字段缺失（BR-03、AI-03 失败行为）纯提示词要求"只输出 JSON"，但无法拦截违规输出
存储SQLite（结构化）+ 本地文件系统（音频、导出）单机单用户场景足够，零运维纯 JSON 文件：简单但并发与查询能力弱
术语库版本化 JSON/CSV 文件（可导入 SQLite 加速）便于人工审核与 diff，符合 NFR-10直接写进代码常量，但不可维护与回溯
评测Python + 编辑距离库（如 jiwer）计算 CER/WER与学术定义一致，结果可复现手工抽样比对，但无法覆盖 1 小时语料

关键取舍说明

  1. 准实时而非流式：录音结束后统一处理，避免在音频不完整时反复触发抽取与生成（PRD §4.3）。
  2. 不做微调：MVP 阶段用提示工程 + 术语库 + 模板约束达到可验证效果；微调需要数据规模，列入长期计划（PRD §3）。
  3. 模板用声明式定义：模板以 JSON 描述字段（key/label/required/order），新增报告类型只需新增文件，不改代码。
